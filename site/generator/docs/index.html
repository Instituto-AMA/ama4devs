Kinds & fields

The core generation engine supports 12 distinct kinds. Standalone document kinds (cpf, cnpj, cnh, pis, rg) produce an object containing value and optional formatted representations, while complex entity kinds return rich structured objects.

person

Realistic individual with valid documents, contact details, and address matching the individual's location:

  • name (string): Full name
  • firstName (string): Given name
  • lastName (string): Family name
  • gender ('F' | 'M'): Gender indicator
  • birthDate (string): Birth date formatted as YYYY-MM-DD
  • age (number): Calculated age in years relative to now
  • cpf (string): Valid CPF check digits
  • rg (string): SP identity document number
  • cnh (string): 11-digit DENATRAN driver license number
  • pis (string): 11-digit mod-11 PIS number
  • motherName (string): Mother's full name
  • email (string): Safe email address on an RFC 2606 domain
  • mobilePhone (string): DDD matching address city + 9 + 8 subscriber digits
  • phone (string): Landline phone (DDD + [2-5] + 7 digits)
  • address (object): Complete nested address object

company

Brazilian business entity with active tax numbers, partners, and CNAE activity:

  • corporateName (string): Legal entity name (Razão Social)
  • tradeName (string): Commercial name (Nome Fantasia)
  • cnpj (string): Valid CNPJ branch 0001
  • stateRegistration (string): State tax registration (Inscrição Estadual)
  • municipalRegistration (string): Municipal registration (Inscrição Municipal)
  • openingDate (string): Formation date formatted as YYYY-MM-DD
  • size ('MEI' | 'ME' | 'EPP' | 'DEMAIS'): Company size
  • activity (object): { cnae: string, description: string }
  • email (string): Company contact email
  • phone (string): Landline phone
  • mobilePhone (string): Mobile phone
  • website (string): Domain format https://www.slug.example.com
  • address (object): Company address
  • partners (array): 1 to 3 person objects (minimum age 21, matching state)

address

Postal address with verified Brazilian postal code (CEP) range and IBGE code:

  • postalCode (string): 8-digit postal code within the city's assigned range
  • street (string): Street type and name
  • number (string): Building number (or 'S/N')
  • complement (string): Apartment, suite, room, or empty
  • district (string): Neighborhood name (Bairro)
  • city (string): Municipality name
  • state (string): 2-letter state abbreviation (UF)
  • stateName (string): Full state name
  • ibgeCode (string): Official 7-digit IBGE city code
  • country (string): 'Brasil'

credit-card

Test credit card details with expiration dates in the future:

  • holderName (string): Cardholder name
  • number (string): 16-digit card number (4444444444444444 for APPROVE, 5184019740373151 for DECLINE, or random Luhn-valid)
  • brand (string): Card network (Visa, Mastercard, Elo, Amex)
  • expiryMonth (string): 2-digit month (01–12)
  • expiryYear (string): 4-digit expiration year (1 to 6 years ahead of now)
  • ccv (string): 3-digit security code
  • outcome ('APPROVE' | 'DECLINE' | 'UNKNOWN'): Configured transaction result

bank-account

Bank account with verified Brazilian clearing codes:

  • bank (object): { code: string, name: string, ispb: string }
  • agency (string): 4-digit branch code
  • agencyDigit (string): Branch check digit
  • account (string): Account number
  • accountDigit (string): Account check digit
  • type ('CONTA_CORRENTE' | 'CONTA_POUPANCA'): Account type

pix-key

Pix identification key:

  • type ('CPF' | 'CNPJ' | 'EMAIL' | 'PHONE' | 'EVP'): Key category
  • key (string): Generated key value (UUIDv4 for EVP, E.164 format for phone)

charge

Financial invoice or charge for payment processing:

  • billingType ('PIX' | 'BOLETO' | 'CREDIT_CARD'): Payment method
  • valueCents (number): Total amount in centavos
  • value (number): Amount in BRL with 2 decimal places
  • dueDate (string): Due date between 0 and 30 days after now
  • description (string): Line-item service or product description
  • externalReference (string): Unique identifier prefixed with GEN-

Document Kinds (cpf, cnpj, cnh, pis, rg)

Stand-alone document generations produce:

  • value (string): Digits-only string (SP RG check digit may be 'X')
  • formatted (string, optional): Masked string when formatted=true (e.g. 123.456.789-09)

Query parameters

The GET /v1/:kind endpoint accepts the following query parameters:

Parameter Type & Default Description
count Integer (1–1000, default 1) Number of items to generate. Values outside range are automatically clamped.
seed String (default random) Seed for the deterministic PRNG. Same seed produces identical items.
formatted Boolean (default false) When true, applies standard punctuation and masks to documents, phones, and CEPs.
state String (2-letter UF) Restricts generated address, DDD, and registration numbers to the specified state (e.g. SP, RJ, MG).
gender 'F' | 'M' Specifies name list and gender for person kind.
outcome 'APPROVE' | 'DECLINE' | 'RANDOM' Applies to credit-card. APPROVE yields 4444..., DECLINE yields 5184..., and RANDOM produces Luhn-valid card numbers.
billingType 'PIX' | 'BOLETO' | 'CREDIT_CARD' Forces payment method for charge kind.
now Date / YYYY-MM-DD Reference date for age calculation, card expiration, and charge due dates. Defaults to current server time.

Determinism

All core generation functions use an internal mulberry32 pseudo-random number generator initialized from the provided seed string. There is no call to Math.random() inside the core generation modules.

Given identical inputs (kind, seed, parameters, and reference date now), the output is guaranteed to be 100% identical. This makes the generator ideal for end-to-end regression suites, reproducible snapshot tests, and deterministic database fixtures.

Safe data guarantees

Generated data is designed never to collide with real-world credentials or deliver emails to unintended recipients:

  • RFC 2606 Domains: All email addresses use reserved testing domains (example.com, example.org, example.net).
  • Websites: Formatted with RFC 2606 domains as https://www..example.com.
  • Test Cards: Approvals and declines use the well-known test card numbers accepted by the Asaas mock (4444444444444444 and 5184019740373151).
  • Phone numbers: Adhere to telecommunication standards without repeated subscriber digits, preventing spam flags during automated tests.

Asaas population

The POST /_mock/asaas/populate endpoint populates the Asaas mock server with customers and payments in a single operation.

Automatic Discovery Both Ways

The Asaas mock looks for the generator on boot and every 10 s at the compose service generator (or generator-mock), on this machine (localhost) and on the Docker host (host.docker.internal), port 45450, the closest first, and takes a place only when it answers GET /health with service: "generator". When GENERATOR_URL is set, it is used as given; set empty, it is turned off. GENERATOR_UI_URL (default http://localhost:45450) specifies where the browser opens it.

The generator finds the Asaas mock by itself when ASAAS_URL is unset: it probes asaas, asaas-mock, localhost, and the Docker host on port 45445, identified by its /health endpoint, on boot and every 10 s. Thus, running both via docker run or within any Docker Compose setup requires no URL environment variables.

The Panel Integration

While the generator is found, the Asaas panel displays an Integrations › Generator tab showing connection status, an "Open generator" link, and a "Populate this account" button. Clicking it creates customers (people and companies with valid CPF/CNPJ) for the account selected in the topbar, registers charges by Pix, boleto, and card, and marks a configurable share of them as paid. This executes through that account's API key via POST /_admin/generator/populate. When the generator is not found or turned off, the tab does not exist.

Request Body

{
  "people": 5,
  "companies": 2,
  "chargesPerCustomer": 2,
  "billingTypes": ["PIX", "BOLETO", "CREDIT_CARD"],
  "confirm": 0.5,
  "seed": "optional-seed",
  "apiKey": "optional-account-api-key"
}

Execution Steps

  1. Target Account: Uses the apiKey specified in the request body to authenticate against Asaas, defaulting to the server's configured ASAAS_API_KEY if omitted.
  2. Create Customers: For each person and company generated, issues a POST /v3/customers request to the Asaas mock API.
  3. Create Payments: For each customer, creates charges using POST /v3/payments matching the specified chargesPerCustomer and billingTypes.
  4. Confirm Payments: Based on the confirm ratio (0.0 to 1.0), issues POST /v3/sandbox/payment/{id}/confirm to transition selected charges from pending to confirmed/received status.
  5. Report Results: Returns an array of customer IDs, payment records with invoice links, and an errors array listing any failed steps with status codes and error messages.

Direct Data credit check

The generator answers the Direct Data API v3 credit routes the Hub uses, at the provider's own paths, faithful to the provider's documentation. The generator never calls the provider: every answer is computed locally, and the only token it accepts is the public 00000000-0000-4000-8000-00000000d1d1 — no real token ever lives in this repository.

Simulated data. Everything the credit check answers is generated automatically for tests: the score, the band, the restrictions and the situation of the CPF are not real and must never be used as a source of truth about any person. Not affiliated with Direct Data, Quod or Boa Vista.

Online, with no container: every test CPF has its answer on Pages, the body the container gives for the synchronous call, at the provider's route names. generator/api/directd.json lists the CPFs and the status the container answers (Pages itself always answers HTTP 200).

curl https://instituto-ama.github.io/ama4devs/generator/api/Score/11100000143
curl https://instituto-ama.github.io/ama4devs/generator/api/BoaVistaAcertaMaisPositivoPF/11100333460
curl https://instituto-ama.github.io/ama4devs/generator/api/DossieCreditoCompleto/11100333460

Try every route in the playground, answered by the public endpoint, by the page itself (any CPF, token and async, with the same core) or by your container (its /api routes send CORS).

A valid CPF outside the table follows one of three policies:

Policy What it answers
lowRisk The low risk preset (the default, and the value of DIRECTD_UNLISTED)
derived A profile drawn from the CPF itself with the seeded rng: the same CPF always draws the same person
notFound 404, as if the document were unknown

Using it from an application

The application points at the generator by its URL — in this repository's compose, the service name:

DIRECTD_MOCK_URL=http://generator:45450

Outside compose, with the container published on the host:

DIRECTD_MOCK_URL=http://localhost:45450

The webhook

The mock answers the provider's webhook routes, at the provider's own paths. The token comes in the Token header, the way the provider takes it there. The handshake has three steps and only the third one confirms the URL: the receiver's URL is registered, the mock posts a code to it, and the receiver sends that code back to POST /api/Webhook/ConfirmUrlCallBack. The 201 the receiver answers to the code message confirms nothing — only ConfirmUrlCallBack confirms the URL.

Route What it answers
POST /api/Webhook/CreateUrlCallBack Registers the URL of the receiver (200); the mock posts the code to it
POST /api/Webhook/ConfirmUrlCallBack Confirms the code the receiver got (200); this is the only thing that confirms the URL 
# Register the URL of the receiver (200). The mock posts the code to it.
curl -s -X POST 'http://localhost:45450/api/Webhook/CreateUrlCallBack' \
  -H 'Token: 00000000-0000-4000-8000-00000000d1d1' \
  -H 'content-type: application/json' \
  -d '{"Url":"http://localhost:45451/webhooks/directd"}'

# The registration: the URL, the code and whether it is confirmed.
curl -s 'http://localhost:45450/_mock/directd/webhook'

# Confirm the code the receiver got (200).
CODE=$(curl -s 'http://localhost:45450/_mock/directd/webhook' | grep -o '"code": "[^"]*"' | cut -d'"' -f4)
curl -s -X POST 'http://localhost:45450/api/Webhook/ConfirmUrlCallBack' \
  -H 'Token: 00000000-0000-4000-8000-00000000d1d1' \
  -H 'content-type: application/json' \
  -d "{\"Code\":\"$CODE\"}"

The mock never leaves the machine: it posts only to a loopback host (127.0.0.1, ::1, localhost) or to a single-label host (a service of a compose network, like hub-webhooks). Any other URL is refused with 400 and nothing is posted, and a redirect from the receiver is not followed.

The callback of a consultation carries the documented keys, in this order — Product, Id, Status and Url:

{
  "Product": "APIv3",
  "Id": "direct-6b1f0d1e-6a5e-4a6c-9a5a-6f5f0d1e6a5e",
  "Status": "Finished",
  "Url": "http://localhost:45450/api/Historico/ObterRetornoConsultaAsync?ConsultaUid=direct-6b1f0d1e-6a5e-4a6c-9a5a-6f5f0d1e6a5e"
}

Status is Finished when the consultation succeeded and Error when it failed.

An async consultation with Callback=habilitar and a confirmed URL settles alone: about one second after the 201 (25 s for the slow CPF 11101444401) the mock posts the callback once, and the first read of the result answers 200 right away. The CPF 11101555572 never settles on its own: only release or fail settles it. Without a confirmed URL nothing is posted and the read rule stays as it was — 202 on the first read, 200 from the second on. A synchronous consultation has nothing to announce: the flag is recorded and nothing is posted.

Whether a URL is confirmed matters at two moments. When the consultation is created, it decides whether the consultation settles alone. When the consultation settles, it decides where the callback goes: to the URL confirmed at that moment, even if a new registration replaced the first one. A registration cleared or replaced by an unconfirmed one in between stops the post, not the settling: the first read still answers 200.

The control routes drive the webhook from a script:

Route What it does
GET /_mock/directd/webhook The registration: { url, confirmed, code }
DELETE /_mock/directd/webhook Clears the registration
POST /_mock/directd/webhook/fire Posts a callback now: { "product": "APIv3", "id": "…", "status": "Modified" }; the availability notice { "product": "APIv3-StatusAvailability", "status": "available" } takes any status word and posts { Product, Status }; it settles no consultation; 409 when nothing is confirmed
POST /_mock/directd/queries/{uid}/release Settles a query now and posts its callback, when it asked for one
POST /_mock/directd/queries/{uid}/fail Settles a query with a failure: { "outcome": "notFound" } (notFound, timeout, unavailable or internalError); the read answers that failure and the callback, when the query asked for one, carries Status: Error; 409 once the query was read or its callback went out, so the read never contradicts what the receiver was told

The balance and the consumption

The mock keeps a balance: it starts at DIRECTD_BALANCE (500 by default) and every consultation the provider charges subtracts the cost of its product — Score 1.98, BoaVistaAcertaMaisPositivoPF 11.18, BoaVistaAcertaCompletoPositivoPF 14.03 and DossieCreditoCompleto 6.99. A balance shorter than the cost answers the 403 of the Saldo insuficiente outcome, and nothing is charged. Both routes take the token in the Token header.

Route What it answers
GET /api/Marketplace/GetBalance The balance of the account
GET /api/Billing/GetConsumptionApiV3 The consumption of the account, and whether its billing is active 
# The balance of the account (200).
curl -s 'http://localhost:45450/api/Marketplace/GetBalance' \
  -H 'Token: 00000000-0000-4000-8000-00000000d1d1'

# The consumption of the account (200).
curl -s 'http://localhost:45450/api/Billing/GetConsumptionApiV3' \
  -H 'Token: 00000000-0000-4000-8000-00000000d1d1'

The control routes drive the balance and the account from a script:

Route What it does
GET /_mock/directd/balance The balance, the same body the provider route answers

What is not simulated

  • The resultadoId and resultado of 202, 400, 403, 404, 408, 500, 503 and of Sucesso com Ressalvas are the simulator's own choice: the provider documents only 1 Sucesso and 3 Não Autorizado.
  • consultaUid and chave are null when the call is refused before a consultation exists (400, 401, 403), and set when the consultation itself failed (404, 408, 500, 503).
  • The texts of faixaScore, perfil, capacidadePagamento, rendaPresumida.faixa and every other descriptive field are plausible values, documented per scenario above.
  • Callback=habilitar on an async consultation asks for a callback: the mock posts it to the URL of a confirmed registration, and to nowhere else. On a synchronous call it only records the flag.
  • GERARCOMPROVANTE=Habilitar only records the flag: no PDF is produced and urlComprovante stays null.
  • GET /api/Historico?ConsultaUid= (the { info, retorno } form) is not simulated.
  • The 429 is forced by its test CPF only: the mock counts no requests per second, and retryAfterSeconds is always 30 (no progressive block).
  • Async=habilitar on a CPF that fails answers the failure at once, with no 201; the slow CPF waits only on a synchronous call — its async consultation is created at once.
  • The async read answers 202 on the first read and the final envelope from the second on (or at once after a release, a failure, or the autonomous settle of a consultation with a confirmed callback URL); an unknown ConsultaUid answers 404 named Obter Retorno Consulta Async.
  • The parameter names are read whatever their case (cpf, async, token).

The generator never calls the provider

The simulation never proxies or forwards a call to the provider: every answer is computed locally from the test CPF table. The only call the mock makes is the callback to a local receiver (a loopback or a single-label host), and the only token it accepts is the public 00000000-0000-4000-8000-00000000d1d1 — no real token ever lives in this repository.

Configuration

The generator server is configured via environment variables:

PORT 45450 Port the HTTP server listens on.

Docker Compose

In another project's compose, add a generator service next to asaas. Both find each other automatically by service name without requiring any configuration variables:

  generator:
    image: ghcr.io/instituto-ama/generator-mock:0.4.0
    ports:
      - '45450:45450'
    depends_on:
      - asaas

Local guard

To prevent unauthorized access or cross-site request attacks against developer environments, the server enforces a Host and Origin security guard on the root UI route (/) and mock management endpoints (/_mock/*).

Allowed hosts default to localhost, 127.0.0.1, ::1, and host.docker.internal. On POST requests, the Origin header is validated against the permitted origins. Public API endpoints under /v1/* remain unrestricted with Access-Control-Allow-Origin: *.
