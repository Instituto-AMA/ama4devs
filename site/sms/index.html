Local SMS gateway with a live handset inbox.

Send SMS via a clean REST API, simple endpoints, or your existing Twilio SDK. Watch messages advance through queued, sent, and delivered with realistic timing, extract OTP verification codes automatically, trigger delivery failures with magic numbers, and test signed webhooks without real carrier credentials or fees. Zero dependencies, in-memory, and paired with a real-time web panel.

Which port it runs on.

The SMS mock answers on port 8899: the panel, the API and the live feed share it. Bound to 127.0.0.1, so only your machine reaches it.

WhatAddressHow to change it
Panel, API and /wshttp://localhost:8899SMS_PORT in .env moves the host port; the container always listens on 8899

The other mocks keep their own ports, so they can run side by side: WhatsApp 3010, Asaas 45445, generator 45450, Mailpit 8025. When another service already holds 8899, publish the SMS mock on a free host port and point your app at it.

It starts with the Asaas mock.

In this repository the root make up brings the SMS mock up together with the Asaas mock, the generator and Mailpit. There is nothing to configure: the Asaas mock finds the SMS mock by itself and sends the payer SMS to it.

How it comes up

make up                 # the asaas profile: SMS mock, Asaas mock, generator, Mailpit
make up MOCKS=sms       # only the SMS mock

Put SMS_ENABLED=0 in .env to keep the SMS mock down; the Asaas mock then finds nobody to send to.

How the Asaas mock finds it

The Asaas mock (version 0.11.0) looks for the SMS mock where it usually answers: the compose service name sms (then sms-mock), this machine, and the Docker host — always on port 8899. It posts the payer SMS to POST /v1/messages with the sender ASAAS, for the same charge events as its e-mails and its WhatsApp messages, and only for the customers that have a mobile phone.

What it gives.

Everything you need to test SMS notifications, authentication codes, delivery reports, and two-way conversations locally.

Capability Description Detail
Lifecycle Automatic transitions: queued → sent → delivered Configurable delay via SMS_DELIVERY_DELAY_MS (default 1500 ms) or manual stepping
Magic numbers Deterministic failures based on the last 4 digits of the recipient number 0001 failed, 0002 undelivered, 0003 rejected (400), 0004 stuck, 0005 filtered
OTP extraction Identifies 4–8 digit verification codes from message bodies Surfaced in JSON response, long-poll queries, and one-click copy chips in the panel
Encoding & segments Full GSM-7 and UCS-2 segment calculation 160/153 chars for GSM-7; 70/67 chars for UCS-2 with emoji and Unicode support
Twilio API Drop-in compatibility for Twilio SDKs and HTTP clients /2010-04-01/Accounts/{sid}/Messages.json with form body and status callbacks
Webhooks Signed delivery receipts and inbound notifications Dispatched on lifecycle events and inbound replies; signed with HMAC-SHA256
Live panel Interactive phone-inbox web UI over WebSocket (/ws) Conversation threads, an OTP chip that copies the code, a details drawer with the JSON and the status history, the reply composer, and a control panel with the delivery, webhook, event, magic-number and API tabs

Use cases.

From verifying OTP login flows in automated test suites to testing carrier failures and webhook retries, the mock handles common communication patterns without third-party services.

Test an OTP login flow

When testing authentication or passwordless login, your test suite can send a verification SMS and read back the generated code via the long-polling query endpoint without polling loops or arbitrary wait timers. The extracted code is also available in the codes array.

curl -X POST http://localhost:8899/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to":"+5511912340010","body":"Your verification code is 481920"}'

curl 'http://localhost:8899/v1/messages?to=%2B5511912340010&wait=5000'

Test delivery failures

Trigger carrier errors and delivery status changes deterministically using the last 4 digits of the recipient number. Test how your application responds to undelivered SMS, blacklisted numbers, or immediate API rejections without changing server code.

# 0001: fails delivery with error 30003
curl -X POST http://localhost:8899/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to":"+5511912340001","body":"Test failure"}'

# 0003: rejected immediately by the API with HTTP 400
curl -X POST http://localhost:8899/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to":"+5511912340003","body":"Test rejection"}'

Step the delivery by hand

Proves your application when the handset takes its time: with the delivery in manual mode the message waits in the queue, and every bubble of the panel can be moved by hand to delivered, failed or undelivered.

curl -X PUT http://localhost:8899/_mock/sms/settings \
  -H 'Content-Type: application/json' \
  -d '{"autoDeliver":false}'
# the message stays queued until you move it

Test webhooks

Verify that your application handles delivery receipts and inbound messages correctly. Provide a callbackUrl per message or configure SMS_WEBHOOK_URL. Webhooks include the x-sms-signature header when SMS_WEBHOOK_SECRET is configured. You can also simulate an inbound reply from a handset:

curl -X POST http://localhost:8899/_mock/sms/inbound \
  -H 'Content-Type: application/json' \
  -d '{"from":"+5511912340010","body":"SIM"}'

Point a Twilio SDK at the mock

Reuse your existing Twilio integration by overriding the API base URL to http://localhost:8899. The mock accepts Twilio form-encoded requests, authenticates mock credentials, and delivers status callbacks formatted to Twilio standards.

curl -X POST http://localhost:8899/2010-04-01/Accounts/ACmock/Messages.json \
  -u ACmock:mocktoken \
  -d "To=+5511912340010" \
  -d "From=AMA4DEVS" \
  -d "Body=Testing Twilio compatibility"

The API, inside the panel

Proves your client against the real contract: the control panel carries the whole catalog of the API — 20 operations, with the parameters, the body fields, a curl and every documented answer — and a Testar button that sends the request for real and shows the answer.

The API in one table.

A lightweight HTTP server with zero runtime dependencies. Includes native JSON endpoints, Twilio compatibility, simple send routes, and internal control tools. The full reference of the API, with every parameter and every documented answer, is on its own page.
