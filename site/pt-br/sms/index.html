O gateway de SMS da sua aplicação, sem depender da operadora.

A sua aplicação envia, o mock captura. Três interfaces para enviar (nativa em JSON, compatível com Twilio e um GET/POST simples), um ciclo de vida de verdade (queued → sent → delivered, ou a falha), números mágicos que reproduzem os erros da operadora, o código de OTP extraído do texto, webhooks de status e de resposta assinados com HMAC — e um painel ao vivo onde você é o aparelho, no localhost.

docker run --rm -p 127.0.0.1:3020:3020 ghcr.io/instituto-ama/sms-mock:latest
Início rápido Casos de uso

O que ele entrega.

O comportamento de uma operadora, sem a operadora: o que a sua aplicação envia, o que chega, quanto custa e o que falha.

Recurso O que faz Na prática
Ciclo de vida A mensagem sai de queued, passa por sent e chega a delivered — ou termina em failed e undelivered sent em 500 ms, delivered em 1500 ms
Números mágicos Os quatro últimos dígitos do destino decidem o desfecho da mensagem final 0001 → failed com código 30003
Extração de OTP Varre o corpo e encontra o código de verificação, de 4 a 8 dígitos "código 482913" → codes: ["482913"]
Segmentos Conta as partes cobradas do texto, em GSM-7 ou UCS-2 160 e 153 caracteres no GSM-7, 70 e 67 no UCS-2
API compatível com Twilio O mesmo caminho, os mesmos corpos de formulário e os mesmos códigos de erro do Twilio POST /2010-04-01/Accounts/{sid}/Messages.json
Webhooks Uma chamada a cada mudança de status e outra quando o aparelho responde, com assinatura HMAC x-sms-signature: sha256=…
Long poll A listagem espera a mensagem chegar, para o teste não precisar de sleep GET /v1/messages?wait=5000
Painel ao vivo A caixa do aparelho, com as conversas por número, atualizada por WebSocket ws://localhost:3020/ws

Números mágicos.

O destino decide o desfecho pelos quatro últimos dígitos. O mesmo número falha em qualquer máquina, em qualquer teste.

Final do número Desfecho Status final Código Resposta HTTP
0001 Handset inalcançável failed 30003 201
0002 Handset desconhecido undelivered 30005 201
0003 Rejeitado pela API, na hora do envio — 21211 400
0004 Parece enviado e nunca confirma a entrega sent — 201
0005 Filtrado pela operadora failed 30007 201
qualquer outro Entrega normal delivered — 201

Casos de uso.

Quatro problemas que aparecem na hora de integrar qualquer envio de SMS.

Testar um login com OTP

O código sai do texto, não de um regex no seu teste: o mock separa a sequência de 4 a 8 dígitos do corpo, guarda em codes e mostra um botão de copiar no painel. Aponte a sua aplicação para o mock, mande o código para um número fixo e o teste acompanha a entrega como ela acontece: enfileirado, enviado, entregue.

curl -X POST http://localhost:3020/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to": "+5511912340010", "body": "Seu código de verificação é 482913"}'

Testar as falhas de entrega

O número que termina em 0001 sempre falha com o código 30003, o 0002 fica undelivered com 30005 e o 0004 nunca passa de sent. Com isso o seu tratamento de erro é exercitado com o mesmo número, na sua máquina e no CI, sem depender de uma operadora real.

curl -X POST http://localhost:3020/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"to": "+5511912340001", "body": "Teste de falha na entrega"}'

Testar os webhooks

Aponte SMS_WEBHOOK_URL para a sua aplicação e receba message.status a cada mudança de status e message.inbound quando o aparelho responde. Com SMS_WEBHOOK_SECRET cada chamada vem com o header x-sms-signature: sha256=<hmac> do corpo, para você validar a assinatura como faria em produção.

docker run --rm -p 127.0.0.1:3020:3020 \
  -e SMS_WEBHOOK_URL=http://host.docker.internal:4000/webhooks/sms \
  -e SMS_WEBHOOK_SECRET=my-app-secret \
  ghcr.io/instituto-ama/sms-mock:latest

curl http://localhost:3020/_mock/sms/webhooks/deliveries

Apontar um SDK da Twilio para o mock

O caminho /2010-04-01/Accounts/{sid}/Messages.json, os corpos de formulário e os códigos de erro são os do Twilio. Troque a URL base do cliente e o seu código de produção continua igual; qualquer credencial é aceita, porque o mock não valida token.

curl -X POST http://localhost:3020/2010-04-01/Accounts/ACmock00000000000000000000000000/Messages.json \
  -u ACmock00000000000000000000000000:mock-auth-token \
  -d "To=+5511912340010" \
  -d "From=AMA4DEVS" \
  -d "Body=Seu codigo e 482913"

A API numa tabela.

Três interfaces de envio, uma de controle e um WebSocket. Tudo em memória, tudo no seu localhost.

Método e rota Descrição Resposta de sucesso
GET /health Verificação de saúde do serviço {"status": "ok", "service": "sms", "version": "..."}
POST /v1/messages Cria e enfileira uma mensagem de saída 201 com a mensagem
GET /v1/messages Lista as mensagens por filtro, com long poll em wait {"messages": [...], "count": 1}
GET /v1/messages/:id Busca uma mensagem pelo identificador Mensagem
DELETE /v1/messages/:id Apaga uma mensagem 204
POST /2010-04-01/Accounts/:sid/Messages.json Envio no formato do Twilio 201 com o recurso do Twilio
GET|POST /sms/send Envio simples, por query ou por corpo {"status": "ok", "id": "...", "to": "...", "segments": 1}
POST /_mock/sms/inbound Resposta escrita pelo aparelho 201 com a mensagem recebida
POST /_mock/sms/messages/:id/status Muda o status de uma mensagem de saída Mensagem
GET|PUT /_mock/sms/settings Lê e muda os ajustes em tempo real {"deliveryDelayMs": 1500, "autoDeliver": true, ...}
GET /_mock/sms/webhooks/deliveries Lista as tentativas de webhook {"deliveries": [...]}
POST /_mock/sms/demo Popula a caixa de exemplo do painel 201 com as mensagens criadas
GET /ws WebSocket com o estado e os eventos do mock Quadros de evento
