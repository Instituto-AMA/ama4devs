WhatsApp Cloud API no localhost.

A Meta Graph API v23.0 da WhatsApp Business Platform, simulada operação por operação a partir da especificação OpenAPI da própria Meta. Mensagens, templates, mídia, ligações de voz, números de telefone e webhooks, mais um painel no estilo WhatsApp Web em que você é o usuário do outro lado da conversa.

https://graph.facebook.com/v23.0
http://localhost:3010/v23.0
docker run --rm -p 3010:3010 ghcr.io/instituto-ama/whatsapp-mock:latest

Abra http://localhost:3010 para ver o painel e aponte a base da Graph API da sua aplicação para http://localhost:3010 no lugar de https://graph.facebook.com. Nada mais muda: mesmos caminhos, mesmos corpos, mesmas respostas, mesmos códigos de erro.

Por quê

Testar uma integração com WhatsApp na Meta exige número de telefone de verdade, empresa verificada, templates aprovados, URL pública para o webhook e conta a pagar por conversa. E mesmo assim você não consegue fazer o usuário responder, atender uma ligação ou ter um template recusado na hora que precisa.

Este mock dá tudo isso no localhost:

  • Fiel por construção. O arquivo OpenAPI da Meta para a v23.0 está no repositório, em spec/v23.0. Toda chamada é roteada e validada por ele, toda resposta segue os schemas de resposta, e um teste de contrato passa todos os exemplos de requisição da especificação da Meta pelo mock. Onde a especificação da Meta contradiz os próprios exemplos da Meta, a correção fica escrita com o motivo (errata.json).
  • Os dois lados da conversa. Sua aplicação envia pela Cloud API; o usuário responde pelo painel (ou pelos seus testes, com um header), e a resposta chega no seu webhook exatamente como a Meta entrega.
  • Estado que se comporta. Templates passam por revisão (aprovado, rejeitado, pausado, com motivo e webhook de status), mensagens vão de enviada a entregue a lida, um número precisa estar registrado para enviar, uma ligação precisa da permissão do usuário.
  • Nada para configurar. Ele já sobe com uma empresa, uma conta do WhatsApp Business e um número registrado com ligações ativas.

O que ele simula

ÁreaCloud APIO que acontece
MensagensPOST /{phone-number-id}/messagesTexto, mídia, localização, contatos, interativas, reações, respostas, templates (cabeçalho, corpo, rodapé, botões, carrossel, oferta relâmpago, autenticação). Recibos enviada → entregue → lida, indicador de digitação.
O usuárioa mesma chamada com X-Mock-FromO usuário escreve, responde, manda mídia e áudio de voz, dá os recibos: a mensagem entra como recebida e vai para o seu webhook.
Templates/{waba-id}/message_templates, /{template-id}Criar, editar, apagar, listar. Revisão com o veredito e o tempo que você escolher, o webhook message_template_status_update, os erros de envio da Meta (132001, 132000, 132012…).
Mídia/{phone-number-id}/media, /{media-id}Upload (multipart, tipos e limites da Meta), consulta, download com token, exclusão. Os arquivos ficam em disco.
Números/{waba-id}/phone_numbers, request_code, verify_code, register, settingsEmpresa → WABAs → números, a ativação de um número novo (o código do SMS aparece no painel), PIN de duas etapas, configuração de ligações. Número não registrado não envia (133010).
LigaçõesPOST /{phone-number-id}/calls, call_permissionsA Calling API com áudio WebRTC de verdade: o usuário liga para a empresa ou a empresa liga para o usuário, com pedido e resposta de permissão, pre_accept, accept, reject, terminate e os webhooks calls.
WebhooksPOST /{phone-number-id} (webhook_configuration)Endereço por número verificado com hub.challenge, assinado com x-hub-signature-256, atraso de resposta opcional e registro de cada tentativa.
O restotodo o restante da especificaçãoRoteado, validado e respondido com o exemplo da própria Meta (Flows, grupos, perfil comercial, QR codes…).

O painel

O painel fala português e inglês (troca no cabeçalho) e não tem rota privada: toda ação é a chamada da Cloud API que sua aplicação faria, ou uma chamada /settings para o que a Meta não tem endpoint.

Ligações e números

O botão de telefone no cabeçalho da conversa faz ligações com áudio WebRTC de verdade, usando o microfone e o alto-falante do navegador. O usuário liga para a empresa (POST /{phone}/calls com X-Mock-From e o offer) e a aplicação recebe calls / connect, respondendo pre_accept / accept com o seu SDP. A empresa liga para o usuário: sem a permissão do usuário, ela envia primeiro o call_permission_request; com permissão, POST /{phone}/calls connect com o offer, e o celular do usuário toca. O pedido de permissão é um card com as opções do usuário — sempre permitir, permitir por 7 dias, não permitir — e a resposta vai para o webhook como call_permission_reply. As ligações ficam na conversa como balões de registro de chamada: atendida com a duração, perdida, recusada.

A aba Números mostra as contas como a Meta organiza: a empresa, suas Contas do WhatsApp Business e seus números. O mock já inicia com o número padrão 1234567890 registrado com ligações ativas. Quando nada está digitado, o botão de enviar vira um microfone, como no celular: grava um áudio de voz (Ogg Opus, mono, 48 kHz, gerado na página via WebCodecs) e envia como audio com voice: true; do lado do usuário, o webhook traz mime_type: audio/ogg; codecs=opus.

  • Criar um número. POST /{waba-id}/phone_numbers com cc, phone_number e verified_name: ele surge não verificado e não registrado.
  • Solicitar o código. POST /{phone-number-id}/request_code; o código que a Meta enviaria aparece no número e em um toast.
  • Verificar. POST /{phone-number-id}/verify_code; um código incorreto retorna (#136025).
  • Registrar. POST /{phone-number-id}/register com o PIN de seis dígitos; o primeiro é salvo, qualquer outro retorna (#133005).
  • Ativar ligações. POST /{phone-number-id}/settings com calling; exige o número registrado e um webhook configurado ((#138018)).
  • Remover da Cloud API. POST /{phone-number-id}/deregister. Um número fora da Cloud API não pode enviar mensagens ((#133010)) nem fazer ligações.

Use no seu projeto

services:
  whatsapp:
    image: ghcr.io/instituto-ama/whatsapp-mock:latest   # ou fixe uma versão: 0.4.1
    ports:
      - '3010:3010'
    environment:
      # Para onde o mock entrega os webhooks (sua aplicação).
      WEBHOOK_URL: http://host.docker.internal:4000/webhooks/whatsapp
      # Assina cada webhook com x-hub-signature-256, como o app secret da Meta.
      WEBHOOK_SECRET: my-app-secret
      # Dentro do container, localhost é o próprio container: isto manda para a sua máquina.
      WEBHOOK_LOCALHOST_REWRITE: host.docker.internal
    extra_hosts:
      - 'host.docker.internal:host-gateway'   # Linux
    volumes:
      - whatsapp-data:/app/data               # conversas, templates, números, mídia
volumes:
  whatsapp-data:

Qualquer Authorization: Bearer <token> é aceito, desde que exista (a Meta recusa a chamada sem ele, e o mock também).

# Sua aplicação envia um template…
curl -X POST http://localhost:3010/v23.0/1234567890/messages \
  -H 'Authorization: Bearer test' -H 'Content-Type: application/json' \
  -d '{"messaging_product":"whatsapp","to":"5511999999999","type":"template",
       "template":{"name":"order_confirmation","language":{"code":"en"},
         "components":[{"type":"body","parameters":[
           {"type":"text","text":"Maria"},{"type":"text","text":"1042"},{"type":"text","text":"29.90"}]}]}}'

# …e o usuário responde (num teste, ou pelo painel).
curl -X POST http://localhost:3010/v23.0/1234567890/messages \
  -H 'Authorization: Bearer test' -H 'Content-Type: application/json' \
  -H 'X-Mock-From: 5511999999999' -H 'X-Mock-Contact-Name: Maria Souza' \
  -d '{"messaging_product":"whatsapp","type":"text","text":{"body":"Oi!"}}'

Headers de teste

O que só um teste precisa vai em headers opcionais, nunca no corpo, para que o corpo continue sendo o que a Cloud API espera:

HeaderEmO que faz
X-Mock-FromPOST /{phone}/messages, /callsA chamada vem do celular do usuário: uma mensagem, um recibo, uma ligação.
X-Mock-Contact-NameidemO nome do perfil que o seu webhook recebe.
X-Mock-Message-Statusum recibo de leitura com X-Mock-Fromdelivered, read ou failed.
X-Mock-Template-Reviewcriar e editar templateAPPROVED (padrão), REJECTED, PAUSED, DISABLED, PENDING.
X-Mock-Template-Review-ReasonidemO motivo da rejeição.
X-Mock-Template-Review-DelayidemQuanto a revisão demora, em ms.
X-Mock-Skip-Callback-Verificationendereço de webhookAceita a URL sem a verificação hub.challenge.

Templates também podem vir de arquivos: cada JSON em templates/ é importado na subida e quando muda, e templates/examples/ traz um exemplo de cada componente que a Meta permite (docs/templates.md).

Desenvolvimento

bun install
bun run src/index.ts server          # http://localhost:3010
bun --bun vitest run --maxWorkers=2  # testes, incluindo o teste de contrato
bun tsc --noEmit

Uma nova versão da Graph API é uma nova pasta spec/<versão> e uma entrada em src/graph/versions.ts; o teste de contrato roda todas as versões.
