WhatsApp Cloud API, on localhost.

The Meta Graph API v23.0 of the WhatsApp Business Platform, simulated operation by operation from Meta's own OpenAPI specification. Messages, templates, media, voice calls, phone numbers and webhooks, plus a WhatsApp Web like panel where you are the user on the other side of the chat.

https://graph.facebook.com/v23.0
http://localhost:3010/v23.0
docker run --rm -p 3010:3010 ghcr.io/instituto-ama/whatsapp-mock:latest

Open http://localhost:3010 for the panel, and point your application's Graph base URL at http://localhost:3010 instead of https://graph.facebook.com. Nothing else changes: same paths, same bodies, same answers, same error codes.

Why

Testing a WhatsApp integration against Meta means a real phone number, a verified business, approved templates, a public URL for the webhook and a bill per conversation. And you still cannot make the user answer, take a call or refuse a template on demand.

This mock gives you all of that on localhost:

  • Faithful by construction. Meta's OpenAPI file for v23.0 is vendored in spec/v23.0. Every request is routed and validated against it, every answer is held to its response schemas, and a contract test sends every request example in Meta's specification through the mock. Where Meta's specification contradicts Meta's own examples, the correction is written down with its reason (errata.json).
  • Both sides of the conversation. Your application sends through the Cloud API; the user answers from the panel (or from your tests, with one header), and the answer reaches your webhook exactly as Meta delivers it.
  • State that behaves. Templates go through a review (approved, rejected, paused, with the reason and the status webhook), messages move from sent to delivered to read, a number has to be registered before it sends, a call needs the user's permission.
  • Nothing to configure. It boots with a business, a WhatsApp Business Account and a phone number already registered with calling enabled.

What it simulates

AreaCloud APIWhat happens
MessagesPOST /{phone-number-id}/messagesText, media, location, contacts, interactive, reactions, replies, templates (header, body, footer, buttons, carousel, limited-time offer, authentication). Receipts sent → delivered → read, typing indicator.
The userthe same call with X-Mock-FromThe user writes, replies, sends media and voice notes, gives receipts: the message enters as inbound and goes to your webhook.
Templates/{waba-id}/message_templates, /{template-id}Create, edit, delete, list. A review with a verdict and a wait you choose, the message_template_status_update webhook, Meta's send errors (132001, 132000, 132012…).
Media/{phone-number-id}/media, /{media-id}Upload (multipart, Meta's types and size limits), describe, download with a token, delete. Files stay on disk.
Phone numbers/{waba-id}/phone_numbers, request_code, verify_code, register, settingsBusiness → WABAs → numbers, the onboarding of a new number (the SMS code shows in the panel), two-step PIN, calling settings. An unregistered number cannot send (133010).
CallsPOST /{phone-number-id}/calls, call_permissionsThe Calling API with real WebRTC audio: the user calls the business or the business calls the user, with the permission request and reply, pre_accept, accept, reject, terminate and the calls webhooks.
WebhooksPOST /{phone-number-id} (webhook_configuration)Per-number override verified with hub.challenge, signed with x-hub-signature-256, an optional response delay, and a log of every attempt.
Everything elsethe rest of the specificationRouted, validated and answered with Meta's own example (Flows, groups, business profile, QR codes…).

The panel

The panel speaks English and Portuguese (switch in the header) and keeps no private routes: every action is the Cloud API call your application would make, or a /settings call for what Meta has no endpoint for.

Calls and numbers

The phone button of the chat header calls with real WebRTC audio, the browser's microphone and speaker. The user calls the clinic (POST /{phone}/calls with X-Mock-From and the offer) and the application hears calls / connect, answering pre_accept / accept with its SDP. The business calls the user: without the user's permission it sends the call_permission_request first; with it, POST /{phone}/calls connect with the offer, and the user's phone rings. The permission request is a card with the user's choices — always allow, allow for 7 days, do not allow — and the answer goes to the webhook as call_permission_reply. Calls stay in the conversation as call log bubbles: answered with the duration, missed, declined.

The Numbers tab shows the accounts as Meta arranges them: the business, its WhatsApp Business Accounts and their numbers. The mock boots with the default number 1234567890 registered with calling on. With nothing typed, the send button is a microphone, as on the phone: it records a voice note (Ogg Opus, mono, 48 kHz, made in the page with WebCodecs) and sends it as audio with voice: true; from the user's side the webhook carries mime_type: audio/ogg; codecs=opus.

  • Create a number. POST /{waba-id}/phone_numbers with cc, phone_number and verified_name: it comes not verified, not registered.
  • Ask for the code. POST /{phone-number-id}/request_code; the code Meta would send shows on the number and in a toast.
  • Verify it. POST /{phone-number-id}/verify_code; a wrong code is (#136025).
  • Register it. POST /{phone-number-id}/register with the six-digit PIN; the first one is kept, another is (#133005).
  • Turn calling on. POST /{phone-number-id}/settings with calling; it needs the number registered and a webhook ((#138018)).
  • Take it off the Cloud API. POST /{phone-number-id}/deregister. A number off the Cloud API cannot send ((#133010)) nor call.

Use it in your project

services:
  whatsapp:
    image: ghcr.io/instituto-ama/whatsapp-mock:latest   # or pin a version: 0.4.1
    ports:
      - '3010:3010'
    environment:
      # Where the mock delivers webhooks (your application).
      WEBHOOK_URL: http://host.docker.internal:4000/webhooks/whatsapp
      # Signs every webhook with x-hub-signature-256, like Meta's app secret.
      WEBHOOK_SECRET: my-app-secret
      # Inside the container localhost is the container: this sends it to your machine.
      WEBHOOK_LOCALHOST_REWRITE: host.docker.internal
    extra_hosts:
      - 'host.docker.internal:host-gateway'   # Linux
    volumes:
      - whatsapp-data:/app/data               # conversations, templates, numbers, media
volumes:
  whatsapp-data:

Any Authorization: Bearer <token> is accepted, as long as there is one (Meta refuses a call without it, and so does the mock).

# Your application sends a template…
curl -X POST http://localhost:3010/v23.0/1234567890/messages \
  -H 'Authorization: Bearer test' -H 'Content-Type: application/json' \
  -d '{"messaging_product":"whatsapp","to":"5511999999999","type":"template",
       "template":{"name":"order_confirmation","language":{"code":"en"},
         "components":[{"type":"body","parameters":[
           {"type":"text","text":"Maria"},{"type":"text","text":"1042"},{"type":"text","text":"29.90"}]}]}}'

# …and the user answers (from a test, or from the panel).
curl -X POST http://localhost:3010/v23.0/1234567890/messages \
  -H 'Authorization: Bearer test' -H 'Content-Type: application/json' \
  -H 'X-Mock-From: 5511999999999' -H 'X-Mock-Contact-Name: Maria Souza' \
  -d '{"messaging_product":"whatsapp","type":"text","text":{"body":"Hi!"}}'

Test headers

What only a test needs travels in optional headers, never in the body, so the body stays what the Cloud API expects:

HeaderOnWhat it does
X-Mock-FromPOST /{phone}/messages, /callsThe call comes from the user's phone: a message, a receipt, a call.
X-Mock-Contact-NamesameThe profile name your webhook sees.
X-Mock-Message-Statusa read receipt with X-Mock-Fromdelivered, read or failed.
X-Mock-Template-Reviewtemplate create and editAPPROVED (default), REJECTED, PAUSED, DISABLED, PENDING.
X-Mock-Template-Review-ReasonsameThe rejection reason.
X-Mock-Template-Review-DelaysameHow long the review takes, in ms.
X-Mock-Skip-Callback-Verificationwebhook overrideAccept the URL without the hub.challenge check.

Templates can also be seeded from files: every JSON in templates/ is imported at start and when it changes, and templates/examples/ brings one example of every component Meta allows (docs/templates.md).

Development

bun install
bun run src/index.ts server          # http://localhost:3010
bun --bun vitest run --maxWorkers=2  # tests, including the contract test
bun tsc --noEmit

A new Graph version is a new spec/<version> folder and an entry in src/graph/versions.ts; the contract test runs every version.
